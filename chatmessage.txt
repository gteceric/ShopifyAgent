The cleanest first version is:

That shape fits MCP well because the server mainly exposes tools for reading order data, checking policy, and producing safe structured outputs. On the MCP side, the official docs still center on tools/resources/prompts, and for local development the simplest path is a stdio server. For remote deployment, the current MCP transport is Streamable HTTP; standalone SSE is deprecated, and remote servers should validate Origin plus add authentication. On the Shopify side, build this against the GraphQL Admin API. Shopify marks the REST Admin API as legacy and says newer platform features may only be available in GraphQL. For order support workflows, the relevant scopes are usually read_orders, often read_all_orders if you need older orders beyond the default 60-day window, and read_returns if you want proper return workflows rather than only refund history.
What your MCP server should expose
Start with five tools:
1. find_order
    * Input: order number, email, name, tracking number
    * Output: matching Shopify order IDs and brief status summary
2. get_order_status
    * Input: Shopify order ID
    * Output: fulfillment status, financial status, tracking info, key timestamps
3. check_refund_eligibility
    * Input: order ID, optional line items
    * Output: your policy result, not just raw Shopify data
4. draft_support_reply
    * Input: order ID + issue type
    * Output: merchant-approved reply draft or structured template
5. log_support_action
    * Input: order ID, tool name, operator, summary
    * Output: audit record ID
The important part is check_refund_eligibility: Shopify gives you refund objects, return objects, and returnable fulfillments for figuring out what can be returned, but “eligible” is still your business rule on top of that. I would implement it as a policy engine: refund window, item type exclusions, tags/VIP overrides, fraud/manual review flags, fulfillment state, prior refund history, and whether Shopify shows returnable fulfillments. Shopify’s docs explicitly position returnableFulfillments as the way to determine items eligible for return before creating a return.

src/index.ts

import "dotenv/config";
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const SHOP = process.env.SHOPIFY_SHOP!;
const TOKEN = process.env.SHOPIFY_ADMIN_TOKEN!;
const API_VERSION = process.env.SHOPIFY_API_VERSION ?? "2026-01";
const REFUND_WINDOW_DAYS = Number(process.env.REFUND_WINDOW_DAYS ?? 30);

if (!SHOP || !TOKEN) {
  throw new Error("Missing SHOPIFY_SHOP or SHOPIFY_ADMIN_TOKEN");
}

async function shopifyAdmin<T>(
  query: string,
  variables: Record<string, unknown> = {},
): Promise<T> {
  const res = await fetch(`https://${SHOP}/admin/api/${API_VERSION}/graphql.json`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-Shopify-Access-Token": TOKEN,
    },
    body: JSON.stringify({ query, variables }),
  });

  const json = await res.json();
  if (!res.ok || json.errors) {
    throw new Error(JSON.stringify(json.errors ?? json, null, 2));
  }
  return json.data as T;
}

const server = new McpServer({
  name: "shopify-support",
  version: "0.1.0",
});

// 1) Find order
server.registerTool(
  "find_order",
  {
    description: "Find Shopify orders by order name/number or email.",
    inputSchema: {
      query: z.string().describe("Examples: '#1001' or 'alice@example.com'"),
    },
  },
  async ({ query }) => {
    const data = await shopifyAdmin<{
      orders: {
        nodes: Array<{
          id: string;
          name: string;
          createdAt: string;
          displayFinancialStatus?: string;
          displayFulfillmentStatus?: string;
        }>;
      };
    }>(
      `
      query FindOrders($q: String!) {
        orders(first: 5, query: $q) {
          nodes {
            id
            name
            createdAt
            displayFinancialStatus
            displayFulfillmentStatus
          }
        }
      }
      `,
      { q: query },
    );

    return {
      content: [
        {
          type: "text",
          text: JSON.stringify(data.orders.nodes, null, 2),
        },
      ],
    };
  },
);

// 2) Get order status
server.registerTool(
  "get_order_status",
  {
    description: "Get the status, tracking, and key details for a Shopify order.",
    inputSchema: {
      orderId: z.string().describe("Shopify GraphQL Order ID"),
    },
  },
  async ({ orderId }) => {
    const data = await shopifyAdmin<{
      order: {
        id: string;
        name: string;
        createdAt: string;
        displayFinancialStatus?: string;
        displayFulfillmentStatus?: string;
        customer?: { displayName?: string; email?: string };
        fulfillments?: {
          nodes: Array<{
            id: string;
            status?: string;
            trackingInfo?: Array<{
              company?: string;
              number?: string;
              url?: string;
            }>;
          }>;
        };
      } | null;
    }>(
      `
      query GetOrder($id: ID!) {
        order(id: $id) {
          id
          name
          createdAt
          displayFinancialStatus
          displayFulfillmentStatus
          customer {
            displayName
            email
          }
          fulfillments(first: 10) {
            nodes {
              id
              status
              trackingInfo {
                company
                number
                url
              }
            }
          }
        }
      }
      `,
      { id: orderId },
    );

    if (!data.order) {
      return {
        content: [{ type: "text", text: `Order not found: ${orderId}` }],
      };
    }

    return {
      content: [{ type: "text", text: JSON.stringify(data.order, null, 2) }],
    };
  },
);

// 3) Check refund eligibility (policy engine + Shopify primitives)
server.registerTool(
  "check_refund_eligibility",
  {
    description: "Evaluate refund eligibility using merchant policy and Shopify returnable fulfillments.",
    inputSchema: {
      orderId: z.string().describe("Shopify GraphQL Order ID"),
    },
  },
  async ({ orderId }) => {
    const basic = await shopifyAdmin<{
      order: {
        id: string;
        name: string;
        createdAt: string;
        displayFinancialStatus?: string;
        displayFulfillmentStatus?: string;
      } | null;
    }>(
      `
      query GetOrderBasic($id: ID!) {
        order(id: $id) {
          id
          name
          createdAt
          displayFinancialStatus
          displayFulfillmentStatus
        }
      }
      `,
      { id: orderId },
    );

    const returnsData = await shopifyAdmin<{
      returnableFulfillments: {
        edges: Array<{ node: { id: string } }>;
      };
    }>(
      `
      query GetReturnableFulfillments($orderId: ID!) {
        returnableFulfillments(orderId: $orderId, first: 20) {
          edges {
            node {
              id
            }
          }
        }
      }
      `,
      { orderId },
    );

    if (!basic.order) {
      return {
        content: [{ type: "text", text: `Order not found: ${orderId}` }],
      };
    }

    const ageDays = Math.floor(
      (Date.now() - new Date(basic.order.createdAt).getTime()) / 86400000,
    );

    const hasReturnableItems = returnsData.returnableFulfillments.edges.length > 0;
    const withinWindow = ageDays <= REFUND_WINDOW_DAYS;

    const eligible = hasReturnableItems && withinWindow;
    const reasons = [
      withinWindow
        ? `Order is within ${REFUND_WINDOW_DAYS}-day refund window`
        : `Order is outside ${REFUND_WINDOW_DAYS}-day refund window`,
      hasReturnableItems
        ? "Shopify reports returnable fulfillments"
        : "No returnable fulfillments found",
    ];

    return {
      content: [
        {
          type: "text",
          text: JSON.stringify(
            {
              orderId,
              orderName: basic.order.name,
              eligible,
              ageDays,
              policyWindowDays: REFUND_WINDOW_DAYS,
              reasons,
            },
            null,
            2,
          ),
        },
      ],
    };
  },
);

// 4) Draft support reply from templates, not blind freeform automation
server.registerTool(
  "draft_support_reply",
  {
    description: "Return a customer support reply draft using approved templates.",
    inputSchema: {
      orderName: z.string(),
      issueType: z.enum(["order_status", "refund_review", "refund_denied", "tracking_delay"]),
      customerFirstName: z.string().optional(),
    },
  },
  async ({ orderName, issueType, customerFirstName }) => {
    const hello = customerFirstName ? `Hi ${customerFirstName},` : "Hi,";
    const templates: Record<string, string> = {
      order_status: `${hello}

Thanks for reaching out about order ${orderName}. I checked the latest order status and tracking details for you. Your order is currently being processed/shipped, and we’ll keep you updated if anything changes.

Best,
Support`,
      refund_review: `${hello}

Thanks for reaching out about order ${orderName}. I’ve reviewed your request and it is currently under refund review. We’ll confirm the outcome as soon as the review is complete.

Best,
Support`,
      refund_denied: `${hello}

Thanks for contacting us about order ${orderName}. I reviewed the request, and this order doesn’t meet our current refund policy requirements. If you believe there are special circumstances, please reply with more details and we’ll take another look.

Best,
Support`,
      tracking_delay: `${hello}

Thanks for checking in on order ${orderName}. I reviewed the tracking and it looks like there may be a carrier delay. We’re continuing to monitor it and will help if the shipment doesn’t update within the expected window.

Best,
Support`,
    };

    return {
      content: [{ type: "text", text: templates[issueType] }],
    };
  },
);

async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error("Shopify Support MCP server running on stdio");
}

main().catch((err) => {
  console.error(err);
  process.exit(1);
});

How to make it safe
This is where most people get sloppy. I would keep the first version read-only except for your internal audit log.
Use these rules:
* Separate read tools from write tools
* Do not let the model issue refunds in v1
* Make check_refund_eligibility advisory only
* Make draft_support_reply template-based
* Redact tokens, addresses, and full payment details from logs
* Log: timestamp, store, order ID, tool called, user/operator, result summary, request hash
* Require a human approval step before any future write action
That matches the direction of the current MCP spec, which added tool annotations for things like read-only vs destructive behavior.
When to add webhooks
Add webhooks as soon as the basic tools work.
Why:
* orders/updated, orders/paid, orders/fulfilled keep order state warm
* refunds/create updates refund history
* returns/request, returns/update, returns/approve, returns/close keep return eligibility context fresh
That gives your MCP tools fast reads from your own cache/audit layer instead of hammering Shopify on every question. Shopify’s webhook references and return-management docs support these order/refund/return flows.
When to move from stdio to remote HTTP
Only after local works.
Move to Streamable HTTP when:
* multiple agents or operators need to use it
* you want centralized auth, rate limits, and monitoring
* the server runs in Docker/Kubernetes
At that point, follow the current MCP transport/security guidance:
* use Streamable HTTP, not old standalone SSE
* validate Origin
* add authentication
* prefer proper OAuth-style authorization for protected remote access

Pass 2

Do not start with “full autonomous customer support.” Start with “support copilot for Shopify order and refund triage.” That will work sooner and be much safer.

More precisely:
MCP is the standard/protocol, and your MCP server is the adapter layer you build. In the MCP architecture, the host app talks to an MCP client, the client talks to the MCP server, and the server exposes capabilities like tools, resources, and prompts to the AI side. MCP is explicitly a client-host-server architecture for connecting AI applications to external systems.
So in your Shopify case, the MCP server does act like an interface between the AI agent and Shopify, but not just a dumb passthrough. It usually does three jobs:
1. exposes standardized tool schemas to the AI,
2. translates those tool calls into Shopify API calls and policy checks,
3. returns structured results back over MCP. MCP tools are discoverable and invokable in a standard way, and they are meant exactly for things like querying APIs or performing controlled actions. 
On the wire, the communication is standardized: MCP uses JSON-RPC, typically over stdio for local servers or Streamable HTTP for remote ones. So yes, the AI side gets a predictable format to work with, but that format is the MCP/JSON-RPC protocol message format, while the actual business payload is whatever your tool returns.
A good mental model is:
AI agent/host → “I need order status” MCP server → calls Shopify GraphQL Admin API, applies your refund/support rules, logs the action → returns structured result AI agent/host → explains it to the user or drafts a reply.
So the subtle correction is:
* Not: “MCP itself receives requests and talks to Shopify”
* Yes: “My MCP server receives standard MCP tool calls, talks to Shopify and my policy layer, then returns results in a standard MCP-compatible way”

Thought for 13s
Yes — if all you do is expose one Shopify API call to one agent, then MCP can be just a wrapper.
That’s the honest answer.
The value shows up when you want the integration to be portable, discoverable, safer, and easier to plug into different AI hosts. MCP is an open standard for connecting AI apps to external systems, with a defined host/client/server architecture, standardized tool schemas, and transport over JSON-RPC. It also standardizes more than “call this function”: servers can expose tools, resources, and prompts, and hosts can discover and use them consistently.
So the difference is:
* Plain wrapper = “I wrote some custom code so my agent can call Shopify.”
* MCP server = “I exposed Shopify support capabilities in a standard way that many MCP-compatible hosts can understand.”
Why that matters:
1. Reuse across hosts Without MCP, your Shopify integration is usually tied to one agent framework or one app. With MCP, the same server can be connected to different MCP hosts because the host-client-server contract is standardized. That is one of MCP’s core goals.
2. Standard tool discovery Instead of hardcoding every function into the agent, the host can discover available tools and their schemas from the server. MCP tools are explicitly defined as named capabilities with metadata/schema so the model can invoke them in a structured way.
3. Separation of concerns Your AI host handles conversation and reasoning; your MCP server handles Shopify auth, API quirks, policy checks, and audit logic. MCP’s architecture is designed around those boundaries, with the host managing permissions/lifecycle and the server exposing capabilities.
4. More than raw API passthrough A useful Shopify MCP server should not merely forward API calls. It can expose:
* a tool like check_refund_eligibility
* a resource like “refund policy config” or “shop support rules”
* a prompt like “draft a refund-review reply in brand tone” Those are native MCP concepts, not just generic wrapper code. 
5. Safer operational layer MCP gives you a cleaner place to add authorization, auditing, rate limits, read-only/destructive boundaries, and approval steps. The current MCP security docs specifically recommend authorization for sensitive resources/operations and call out auditing/usage tracking as reasons to implement it.
So the practical answer is:
* For one solo prototype: a plain wrapper may be enough.
* For something you want to scale, swap hosts, or share with other AI clients: MCP is valuable.
For your Shopify support case, the real value-added is not “MCP magically does more than an API wrapper.” The value is that MCP gives you a standardized contract around your wrapper, and your server becomes a support capability layer rather than a pile of ad hoc API calls.
A good mental model:
Shopify API = raw parts Your business logic = support rules MCP server = standardized adapter/productized interface for AI hosts
So I’d say:
MCP is often a wrapper, but a standardized, host-portable, tool-aware, security-friendly wrapper.
And that difference is why people use it.

import "dotenv/config";

const SHOP = process.env.SHOPIFY_SHOP;
const TOKEN = process.env.SHOPIFY_ADMIN_TOKEN;
const API_VERSION = process.env.SHOPIFY_API_VERSION || "2026-01";

if (!SHOP || !TOKEN) {
  throw new Error("Missing SHOPIFY_SHOP or SHOPIFY_ADMIN_TOKEN in .env");
}

export async function shopifyAdmin(query, variables = {}) {
  const res = await fetch(
    `https://${SHOP}/admin/api/${API_VERSION}/graphql.json`,
    {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "X-Shopify-Access-Token": TOKEN,
      },
      body: JSON.stringify({ query, variables }),
    }
  );

  const json = await res.json();

  if (!res.ok || json.errors) {
    throw new Error(JSON.stringify(json.errors ?? json, null, 2));
  }

  return json.data;
}

export async function findOrders(searchText) {
  const query = `
    query FindOrders($query: String!) {
      orders(first: 5, query: $query) {
        edges {
          node {
            id
            name
            createdAt
            displayFinancialStatus
            displayFulfillmentStatus
            totalPriceSet {
              shopMoney {
                amount
                currencyCode
              }
            }
            email
          }
        }
      }
    }
  `;

  const data = await shopifyAdmin(query, { query: searchText });

  return data.orders.edges.map((edge) => edge.node);
}
